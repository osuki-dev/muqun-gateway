# Range-addressed pane output, and tmux first

## Why

The output endpoint can only say "give me the last N lines". Paging back means
asking for a larger N and receiving everything already held plus a little more.
Two things follow from that, and both are already visible in the code.

The client cannot tell when it has reached the top. `MAX_OUTPUT_LINES` is 5000
while a tmux `history-limit` of 50000 is ordinary, so "N was refused" and "there
is nothing older" look identical from outside. Muqun works around this by
measuring: `hasEarlierAfterPage` in `src/terminal/history.ts` stops promising
more history once a page comes back no longer than the one before it. Its
comment records what that costs — a pane advertising 2765 rows plateaued at 992
returned lines, so the reader pulled at 1200, 1440, 1680 and 1920 and got zero
new bytes four times before the heuristic caught up.

The transfer is quadratic in the depth paged. Reaching line 5000 in 500-line
steps moves about 25× the bytes the content is worth, over a phone link.

A range makes both go away. `start == 0` is the top, as a fact rather than an
inference, and each page carries only its own lines.

## Scope

In:

- Absolute-range addressing for `GET /api/sessions/{id}/panes/{pane}/output`
- tmux serves ranges natively; herdr reports honestly what it served instead
- tmux sorts ahead of herdr among configured sessions
- Muqun pages by range and stops measuring when the range is there

Out:

- The pane-id percent-encoding defect. Muqun interpolates `%14` into the URL
  path unencoded, axum percent-decodes it to `0x14`, and two-digit tmux panes
  404. `src/api/` is generated by fizzyx and the generator is being fixed
  separately. Nothing here depends on it, and nothing here makes it worse.
- Any change to `MAX_OUTPUT_LINES`. It stays 5000, now as a per-request
  ceiling rather than a horizon.

## Coordinates

Absolute line 0 is the oldest line the pane still holds; `total` is one past the
newest. Ranges are half-open, `[start, end)`.

tmux's own coordinates are relative to the top of the *visible* pane: 0 is the
first visible row, negative reaches into scrollback, and `-E` is inclusive.
Measured on a live pane with `history_size = 463` and `pane_height = 41`:

| command | result |
| --- | --- |
| `capture-pane -S -` | 504 lines = 463 + 41 |
| `capture-pane -S -448` | 489 lines = 448 + 41 |
| `capture-pane -S -448 -E -448` | exactly 1 line |
| `capture-pane -S 0 -E 0` | first visible row |

So `total = history_size + pane_height`, and the mapping is:

```
[start, end)  ->  capture-pane -S (start - history_size) -E (end - 1 - history_size)
```

Checks: `start = 0` gives `-S -463`, the oldest line. `start = history_size`
gives `-S 0`, the first visible row. `end = total` gives `-E 40`, which is
`pane_height - 1`, the last visible row.

### The one limitation

tmux exposes no monotonic count of lines ever produced; `history_size` reports
only what is currently retained. Absolute indices are therefore stable until the
pane reaches `history-limit` and tmux begins dropping the oldest lines, after
which previously issued indices shift by the amount trimmed.

This is accepted rather than solved. Solving it means the gateway keeping
per-pane trim state across restarts, to make addressable exactly the lines tmux
has already discarded. Clients that care can notice `total` failing to grow
across two reads that both saw new output.

## Request

`start` and `end` join `OutputQuery` as optional fields. Neither present keeps
today's behaviour exactly, so existing clients are untouched.

```rust
struct OutputQuery {
    source: Option<String>,
    lines: Option<u32>,
    format: Option<String>,
    start: Option<u32>,
    end: Option<u32>,
}
```

| condition | behaviour |
| --- | --- |
| neither given | today's tail-of-`lines` read |
| exactly one given | 400 `invalid_range` |
| `start >= end` | 400 `invalid_range` |
| `end - start > MAX_OUTPUT_LINES` | serve `[start, start + MAX_OUTPUT_LINES)`, report what was served |
| range beyond `total` | clamp; do not error |
| `lines` also given | ignored; the range wins |
| `source=visible` | range ignored; report what was served |

Out-of-bounds clamps rather than failing because a reader scrolling toward the
top will always eventually ask for more than exists, and that is a normal
arrival at the top rather than a client mistake.

## Response

Every read grows a `range`, on both backends:

```json
{ "result": { "type": "pane_read", "read": {
  "output": "...",
  "revision": 1234,
  "range": { "start": 1200, "end": 1700, "total": 50041 }
}}}
```

`range` describes what was served, never what was asked for. A client reads it
rather than assuming its request was honoured, which is what lets one response
shape cover a backend that implements ranges and one that does not.

`start == 0` means the top has been reached. That is the field that replaces
`hasEarlierAfterPage`'s measurement.

## Backends

`ReadPane` gains `start: Option<u32>` and `end: Option<u32>`; `PaneOutput` gains
a `range` describing the lines returned.

**tmux** honours the range through the mapping above. It already queries
`history_size`; `pane_height` comes from the same `display-message` call.

**herdr** ignores `start`/`end` — the `pane.read` wire protocol carries only
`pane_id`, `source`, `format`, `lines`, and herdr is a separate process whose
protocol is not ours to extend. It fills `range` with the tail it actually
returned, always ending at the newest line:

- `total` is herdr's own scrollback count where it reports one, taken from the
  same pane metadata that feeds `max_offset_from_bottom`; where it reports
  none, `total` is the number of lines returned.
- `end = total`, `start = total.saturating_sub(returned_lines)`.

`total` therefore means the same thing on both backends — one past the newest
addressable line — while being derived from whatever each backend actually
knows. A client paging a herdr pane sees `start` stop decreasing and stops
asking, with no capability flag and no backend sniffing.

Note that herdr's count is the metric Muqun already found unreliable (a pane
claiming 2765 rows that yielded 992 lines). Reporting it in `range` does not
make it truer, but it does put it next to the line count it failed to predict,
so a client comparing the two can see the disagreement in a single response
rather than across four.

## tmux first

There is no implicit default backend to change. A fresh `Config` starts with
`sessions: Vec::new()`, and both backends are explicit choices in the setup menu
(`enable_managed_backend(BackendKind::Herdr)` / `(BackendKind::Tmux)`).

What decides which backend the app uses is **order**, because Muqun takes
`sessions[0]` and exposes no picker (`src/stores/session-control.ts:96`). So:

- `enable_managed_backend` places tmux sessions ahead of herdr sessions.
- `BackendKind`'s `#[serde(default)]` stays `Herdr`. It is the contract for
  reading configs written before the field existed — including this machine's
  `default` session, which has no `backend` key and must keep routing to herdr.
  Creation defaults and deserialization defaults are different questions and
  conflating them is what would silently repoint an existing install.

## Muqun

The measuring in `src/terminal/history.ts` exists because herdr's row count
could not be trusted and there was no other signal. With `range` present there
is one, so the app stops inferring:

- `hasEarlierAfterPage` keeps its current body as the no-`range` path, for herdr
  panes and gateways older than this change. When `range` is present the answer
  is `range.start > 0` and nothing is measured.
- Paging changes from "ask for a larger tail" to "ask for the page above the one
  I have": `[max(0, start - pageSize), start)`. Pages are disjoint, so
  `foldPaneRead` prepends rather than replacing the window, and a page costs its
  own lines instead of every line below it.
- The renderer's window cap is unchanged. Prepending past it trims the tail as
  it does today; the pane's live screen is re-read on the next refresh.

The two paths differ only in how "is there more above" is answered and how the
next request is addressed. Merge, sanitize, and render are untouched.

This is the half of the change the user actually sees. The gateway half without
it just moves bytes more efficiently for a client that still guesses.

## Testing

- Unit: the coordinate mapping, anchored to the measured numbers above —
  `start = 0` maps to `-S -463`, `end = total` to `-E 40`, `-E` inclusive.
- Unit: each row of the request table, including that clamping does not error.
- Unit: herdr fills `range` from what it returned, not from what was requested.
- Unit: absent `start`/`end` produces byte-identical behaviour to today.
- Contract (`#[ignore]`, isolated socket): extend the existing tmux scrollback
  test to assert two disjoint ranges do not overlap and that their
  concatenation equals the single read spanning both.
- Muqun unit: `range.start > 0` decides "more above" without consulting line
  counts, and a response with no `range` still takes the measured path.
- Muqun unit: two disjoint pages prepend into one window in order, with no
  duplicated or dropped rows at the seam.
