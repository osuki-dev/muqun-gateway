# v0.13.0

The Gateway now runs several coding agents at once. OpenCode, DeepSeek Harness and T3 Code can all be attached to the same Gateway, every session says which agent owns it, and the App can follow all of them over a single WebSocket. This release also closes a pairing hole in cleartext mode and a session-stream hole after device revocation.

**This release renames parts of the App-facing API and does not keep the old names as aliases.** Muqun App 3.1.0 is the release that speaks the new names; see Compatibility.

## Changes and fixes

### Several agents at once

- **OpenCode, DeepSeek Harness and T3 Code can be attached together.** Each is an *agent* with an id (`opencode`, `deepseek`, `t3`). Sessions carry `agent_id`; creating a session takes `agent_id`; and the session list, catalog, projects and agent status routes take `?agent_id=`. The session list merges every attached agent, and an agent that fails is skipped with a warning instead of turning the whole list into a 502.
- **A request that names no agent goes to the preferred one.** The order is OpenCode, then DeepSeek, then T3. There is no "active" agent in the contract; the order only decides the default. A session the Gateway has no record of after a restart is resolved by asking each attached agent who owns it, and is answered `404` if none does. Before this, it could be sent to the wrong agent.
- **Unknown or detached agents are refused clearly.** An unknown `agent_id` is `400 invalid_agent`; a known one that is not attached is `503 agent_unavailable`, naming the agent.
- **Discovery lists agents in preference order and stays cheap.** `/api/discovery` and `/api/capabilities` describe each agent under `planes.agents` (id, name, kind, status, models, modes, features). The result is cached for about ten seconds behind a single refresh, so polling no longer probes every upstream, and an unauthenticated caller sees no endpoints or versions.
- **Per-agent capability flags.** Each agent's `features` says explicitly whether it supports modes, skills, slash commands, compaction, background shells, attachments, revert, the inbox and worktrees, so the App no longer guesses by agent kind. OpenCode supports all of them; DeepSeek Harness supports modes only (its presets are chosen when a session is created); T3 Code supports none of those, but does support revert and tool approvals.
- **Provider availability.** Catalog providers carry `available`, which is false for a T3 provider that is disabled, not installed or has no models. T3 display names are used when T3 supplies them. A model picker can group by provider and grey out the ones that are not signed in on the host.
- **`stagedRevert` is a declared feature.** It says whether an agent reverts in two steps (stage, then commit). Only OpenCode does; for DeepSeek Harness and T3 Code, staging answers `501 feature_unsupported`, and a T3 revert rolls back whole turns in one step.
- **A T3 server with no credential is `unconfigured`.** When T3 answers but the Gateway has no pairing token or credential to attach with, its status is `unconfigured`, not `connected`, so the App can say pairing is needed. Other statuses are `disabled` and `not_installed`.
- **A session created without a directory opens in the user's home folder** for every agent. DeepSeek Harness used to refuse the relative `.` the App effectively sent.

### T3 Code

- **T3 Code is a new agent**, driven over its WebSocket RPC. Projects and threads become sessions; messages, tool activity, approvals, user-input requests, diffs and reverts map onto the same timeline the other agents use. T3 has no personas, so its `modes` are empty, and its `runtimeMode` is treated as a permission policy. The wire reference is `docs/t3-protocol.md`.
- **It is off until configured.** Add a `t3` block to `config.json`:

  ```json
  { "t3": { "enabled": true, "url": "http://127.0.0.1:3773", "pairing_token": "…" } }
  ```

  `url` defaults to T3's `http://127.0.0.1:3773`; the Gateway tries only that address and never scans. Other keys are `token` (a bearer you already hold, used instead of pairing) and `runtime_mode` (`full-access` by default, `approval-required`, `auto-accept-edits` or `auto`). `T3_URL`, `T3_TOKEN` and `T3_PAIRING_TOKEN` fill unset keys but never enable T3 on their own.
- **Pairing with `t3 pair`.** Run `t3 pair` on the T3 host (with the same `--base-dir` as the server, if it has one). It prints a pairing link ending in `#token=…` and the token on its own line. Put that token in `t3.pairing_token` and restart the Gateway. The Gateway exchanges it once for a long-lived credential, stores it in `t3-credential.json` in its state directory (readable by you only), and never needs the token again. If T3 revokes the credential, pair again with a new token.
- Up to 32 T3 threads are followed at a time; the least recently used is released first.
- **An agent asking a question now reaches the phone.** When an OpenCode, DeepSeek or T3 session -- a sub-agent's child session included -- asks the user to fill a form, every registered device gets one push ("*name* needs your input"), with `type: "question"`, `server_id`, `agent_id`, `session_id` and `form_id` in its data. Before, only approvals pushed. Approval pushes now carry `server_id` too, and a request T3 re-announces no longer pushes again.

### DeepSeek Harness

- **Config key `deepseek`.** DeepSeek Harness is attached only when `deepseek.enabled` is true or an explicit `deepseek.endpoint` is given. Other keys are `token` and `secret` (the cookie signing secret). Nothing is scanned: the old fallback that tried ports 3080 and 19387 and sent the bearer token and cookie to whatever answered there is gone. An explicit endpoint is never followed by a scan.
- **Live events and approvals.** The adapter now delivers session, timeline, status and approval events from the harness, and answers approvals and questions through it. The harness offers allow-once or reject only, so "always" is sent as allow-once. Operations it cannot do (revert, deleting a session, attachments) are refused as unsupported instead of reporting success.
- **Real presets.** Modes come from DeepSeek Harness's own agent presets. The invented `general` mode is gone, which fixes "Agent session not found" on creating a session. A refusal is now reported with its own code, and only a real missing session is a "session not found".
- **Injected context stays hidden.** The runtime, time and skill-catalog records the harness writes into a session no longer show up as messages you sent.
- Client-facing errors are short and static; upstream detail stays in the local log, and the token and secret are redacted in logs.

### WebSocket event channel

- **`GET /api/ws`** gives a paired device one socket that carries agent events for any number of sessions. The client sends `subscribe`, `unsubscribe` or `subscribe_all`, and each frame's `event` and `data` are exactly what the per-session SSE route would have sent. The SSE routes are unchanged.
- **Discovery advertises it** with the `ws_events` capability and `transports.websocket` (path `/api/ws`, protocol 1). API version is now **1.9.0**.
- The handshake is authenticated like the SSE routes. Under encrypted transport every frame is sealed with AES-256-GCM, with keys derived per connection and per direction. `docs/agent-api.md` documents the frames, the derivation and a test vector.
- Falling behind the broadcast becomes a resync for each subscribed session. A protocol ping runs every 25 seconds, the device is rechecked every five seconds and closed if revoked, a device holds at most four sockets (the newest wins) and the Gateway at most 64.

### Renamed: harness and engine are now agent

One word is now used everywhere. **No old name is accepted or emitted.**

| Before | Now |
|---|---|
| persona field `agent` on session create, `agent` on the session, `defaults.agent` in the catalog | `mode`, `defaults.mode` |
| catalog `agents[]` (personas) | catalog `modes[]` |
| catalog `commands[].agent` | `commands[].mode` |
| `agent_switched` part, `agent` and `previous` | `mode` and `previous` |
| `POST /api/agent-sessions/{id}/agent` | `POST /api/agent-sessions/{id}/mode` |
| `GET /api/agent-engine` | `GET /api/agent-status` (takes `?agent_id=`) |
| error `agent_engine_error` (502) | `agent_error` |
| harness / engine ids and aliases in discovery | `planes` is exactly `terminal`, `agents` and `ssh`, with `agents[]`, each with `modes[]` and `features{}` |
| capability for a picker | `multi_agent` |
| selector parameter | `?agent_id=` |

New in the same change: the error code `invalid_agent`, and the session, catalog and projects routes' `agent_id` parameter described above.

### Security and reliability

- **Security fix: the pending pairing code required no credential in cleartext mode.** With transport encryption off, `/api/pair/pending` (the one-time code and request id) and the paired-device list were readable by anyone who could reach the listener, so a pairing could be claimed before the user typed the code. The admin token is now required in every mode. Cleartext mode drops the encryption envelope, not authentication. **If you run cleartext mode on a network you do not fully trust, upgrade, and review your paired devices with `muqun-gateway manage`.**
- **Revoked devices lose their agent stream.** The per-session agent SSE stream never rechecked device revocation, so a revoked device kept receiving events. It now rechecks every five seconds, like the terminal stream and the WebSocket, and closes.

### Command line

- **`muqun-gateway agent`** lists each agent's status, version and endpoint with the next step to take (`agent setup t3`, `opencode service start`, and so on), and exits non-zero while an enabled agent is unusable; `--json` prints the discovery `agents` array. **`agent setup t3`** mints or exchanges a T3 credential, stores it and enables T3; **`agent setup deepseek`** finds a running DeepSeek Harness and enables it. Both offer to restart the gateway's user service when the change needs one.

## Compatibility

- **Muqun App 3.1.0 is required for multi-agent.** It reads `planes.agents`, shows a tile per agent, addresses sessions with `agent_id` and uses `/api/ws`. A newer App against an older Gateway falls back to single-agent mode and says when a feature needs a Gateway upgrade.
- **Older Apps (3.0 and earlier) keep working** against the primary agent (OpenCode when it is attached). Routes and behaviour they rely on are unchanged, with one exception: the persona field is now `mode`, not `agent`, in requests, the catalog and the `agent_switched` part. An older App therefore cannot switch or display OpenCode's `build`/`plan` persona correctly until it is updated to 3.1.0. It also gets `agent_error` where it used to get `agent_engine_error`, and `/api/agent-status` where it used `/api/agent-engine`.
- **API 1.9.0.** Capabilities `multi_agent` and `ws_events` are new. API major remains 1.
- **Herdr:** unchanged from v0.12.2. Terminal integration requires Herdr 0.7.5 or newer. Agent collaboration requires a connected Herdr 0.9.0+ backend.
- **OpenCode:** unchanged, 2.0.15 with an OpenCode 2 server exposing `/api/info`. **DeepSeek Harness** and **T3 Code** (tested with `t3 serve` 0.0.42) are optional.
- **Platforms:** macOS (arm64, x86_64) and Linux (x86_64, aarch64, musl).

## Upgrade

Re-run the installer:

```sh
curl -fsSL https://muqun.dev/gateway.sh | sh
```

The installer replaces the binary and restarts the managed service. If you run the Gateway outside its managed service, **restart it yourself after upgrading**. Configuration migration: none. Existing pairings, device tokens and settings are kept and no re-pairing is needed, and OpenCode keeps working with no config change.

To add another agent, set the `deepseek` or `t3` block described above and restart the Gateway. Update Muqun App to 3.1.0 to use more than the primary agent.
